# ASTRO CONSTRUCTION - PROJECT RULES

## 1. Purpose

This file is the main detailed operating framework for the ASTRO CONSTRUCTION website project.

The website must be treated as a long-term digital product and developed to the quality level expected from a professional digital agency engagement in the 50,000-100,000 EUR range.

The primary goals are:

- visibility in Google and AI search;
- trust;
- qualified leads;
- conversion;
- maintainability;
- technical reliability;
- long-term scalability.

Project Instructions remain the highest-priority instruction layer. This file expands those instructions and must be used together with the relevant specialized project files.

## 2. Decision hierarchy

Use this priority order when instructions or project information conflict:

1. Current explicit user instruction.
2. Project Instructions.
3. Approved project decisions and approved user-facing copy.
4. This file.
5. Relevant specialized project files.
6. Existing implementation patterns in the repository.
7. Older chats, drafts and historical proposals.

Do not silently override an approved decision because another approach appears cleaner or more modern.

If an approved decision creates a material technical, SEO, UX, accessibility, performance, security or maintenance risk, explain the risk and propose the smallest safe correction before implementation.

## 4. Working method

Treat new ideas as hypotheses until they are checked.

For meaningful changes evaluate:

- user value;
- clarity;
- UX;
- conversion impact;
- SEO value;
- GEO/AEO value;
- correctness;
- accessibility;
- security;
- privacy;
- maintainability;
- performance;
- implementation complexity;
- regression risk.

Prefer the strongest rational solution, not the fastest visible change.

Do not create work merely because a possible improvement exists. Each change must solve a real problem, support a verified opportunity or reduce a meaningful risk.

Preserve approved decisions unless new evidence justifies reconsideration.

## 5. Research before major decisions

For major SEO, UX, information architecture, service-page, content or marketing decisions, use current evidence where available.

Relevant sources include:

- Google Search Console;
- GA4;
- Google Business Profile;
- PageSpeed / Core Web Vitals;
- indexing status;
- SERP analysis;
- competitors;
- real search intent;
- site analytics;
- existing conversion paths.

The primary market is Latvia.

Do not create a new SEO page only because a keyword or topic exists.

Before creating a new service page, expert page or major content section, evaluate:

- query demand;
- search intent;
- SERP composition;
- competitor coverage;
- current GSC data;
- overlap with existing ASTRO pages;
- cannibalization risk;
- commercial value;
- ability to provide genuinely useful content.

Avoid duplicate pages with substantially the same user intent.

## 6. Product and UX principles

Treat the site as a product, not as a collection of isolated pages.

Prioritize:

- clear navigation;
- understandable hierarchy;
- fast orientation;
- trust;
- conversion;
- accessibility;
- responsive behavior;
- maintainability.

A user should understand:

- what ASTRO does;
- whether the service matches their situation;
- what happens next;
- what information or documents they need;
- what result they receive.

Do not default to repetitive card grids when a clearer information structure exists.

Use cards only when they improve scanning, comparison or interaction.

Major UI changes must be evaluated on both desktop and mobile.

Check:

- navigation;
- hierarchy;
- typography;
- spacing;
- interactions;
- touch behavior;
- overflow;
- focus behavior;
- accessibility;
- content density;
- Core Web Vitals impact.

## 7. Design principles

The site should feel deliberate, modern, calm and technically credible.

Avoid generic agency aesthetics, excessive decoration and visual patterns that make the site look templated.

Prefer:

- strong hierarchy;
- clear typography;
- real construction material;
- real project documentation;
- drawings;
- diagrams;
- tables;
- process visuals;
- restrained interaction.

Do not introduce new visual systems when an existing design-system pattern can solve the problem.

Changes to shared components must consider all dependent pages.

## 8. Content principles

User-facing construction content must sound like an experienced Latvian construction specialist speaking normally to a client.

The text must be understandable to a non-professional adult.

Prefer:

- short direct sentences;
- concrete actions;
- exact roles;
- exact documents;
- exact conditions;
- exact outputs.

One sentence should normally communicate one main idea.

Every sentence must add information.

Remove filler, ceremonial introductions, bureaucratic wording, repetition and decorative conclusions.

Do not write like:

- legislation;
- a municipality;
- a lawyer;
- a textbook;
- generic AI content;
- corporate marketing copy.

Professional terminology is allowed and encouraged when it is the correct term, but explain it in ordinary language when a client may not understand it.

For BIS, regulatory and technical topics explain the practical meaning first:

- who does what;
- what is prepared;
- what is submitted;
- what is checked;
- what is signed;
- when construction may start;
- what happens next;
- what the client receives.

Legal references and regulatory citations come after the practical explanation.

## 9. No vague generalisations

Never replace verified specific information with a broad umbrella term.

If the exact composition is known, write the full composition.

Instead of a generic word such as "documents", name every document that is relevant.

Instead of "works", name the actual works.

Instead of "actions", name the actual actions.

Instead of "persons involved", name the roles.

Instead of "process", state the steps.

Instead of "requirements", state the exact requirements.

Do not use "etc.", equivalent abbreviations or vague endings to avoid listing known contents.

If composition changes under a defined condition, state that condition and give the complete verified composition for that condition.

If something remains unverified, state exactly what is not yet confirmed.

## 10. Concrete language

Avoid vague substitutes such as:

- noteiktos;
- atsevišķos;
- konkrētos;
- dažos gadījumos;
- atkarībā no situācijas;
- vajadzības gadījumā;
- ja nepieciešams;
- var būt;
- attiecīgais;
- atbilstošs;
- atbilstoša;
- atbilstoši;
- atbilstošās;
- ņemot vērā.

Avoid empty labels such as:

- prasītie dokumenti;
- vajadzīgie dokumenti;
- nepieciešamie dokumenti;
- jāsagatavo nepieciešamā dokumentācija;
- pārējie dokumenti;
- citi dokumenti.

Strictly avoid these constructions in user-facing ASTRO copy:

- atbilstošas darbības sfēras;
- attiecīgās prasības;
- nepieciešamie dokumenti;
- paredzētie darbi;
- konkrētajā situācijā;
- atkarībā no apstākļiem;
- veikt nepieciešamās darbības;
- nodrošināt atbilstošu risinājumu;
- ievērot noteiktās prasības;
- iesniegt attiecīgo dokumentāciju.

Do not replace them with a different vague phrase.

Rewrite the sentence with the exact document, work, action, role, condition, requirement or result.

If a sentence leaves unanswered "what exactly?", "which one?", "when?", "under what condition?" or "what changes?", rewrite it.

## 11. Style restrictions

Do not use stylistic negative-contrast formulas such as:

- Tas nav...
- Šis nav...
- Šī nav...
- nav tikai...
- X nav tikai Y, bet arī Z...
- Runa nav par...
- Nevis X, bet Y...
- Patiesībā...
- Īstenībā...
- X nenozīmē Y...
- Ar X vien nepietiek...
- Nepietiek tikai ar...
- Nevajag jaukt X ar Y...

The phrase "nav tikai" is forbidden regardless of context.

Normal factual negation is allowed when it is needed to state a fact.

Do not use long dashes in user-facing website copy. Use normal punctuation or a hyphen where appropriate.

Do not use "Anonimizēti" as a marketing label.

Do not use "audit" or "audits" as a casual marketing label where a more exact service name exists.

Do not use "koordinējam" when ASTRO itself performs the work.

Do not invent:

- experience;
- clients;
- projects;
- results;
- certificates;
- deadlines;
- prices;
- savings;
- statistics;
- guarantees.

## 12. Commercial page principles

Commercial pages should lead with the client’s practical result or next action.

Put operational detail, legal detail, FAQ content and supporting explanations lower on the page when that structure improves clarity and conversion.

Do not expose internal working mechanics when the client only needs to understand the result, scope, price logic or next step.

Benefits must be concrete and useful.

Approved benefit wording may include:

- ātrāk;
- vienkāršāk;
- mazāk dokumentu;
- mazāks laiks līdz būvniecības uzsākšanai;
- zemākas izmaksas.

State a benefit only when the page content supports it.

## 13. Explaining construction terms and documents

Answer the practical client question, not only the dictionary definition.

A construction term page should normally explain:

- what it means in practice;
- when it is used;
- who prepares or signs it;
- what exact documents or actions are involved;
- what happens after it;
- what the client receives.

Each term should begin with a short practical hook, normally 8-14 words.

Use "Kas tas ir?" when useful, but do not force one template onto every topic.

Use "Svarīgi" only for a real limitation, exception, transition rule or obsolete term.

Prefer examples based on real construction situations when they improve understanding.

Add exceptions only when they change the user’s decision or action.

## 14. SEO

SEO must be considered together with product usefulness and conversion.

For relevant pages check:

- search intent;
- indexing;
- title;
- meta description;
- H1;
- heading hierarchy;
- internal links;
- canonical;
- structured data;
- crawlability;
- page duplication;
- CTR opportunity;
- image SEO;
- performance;
- content usefulness.

Do not optimize text by making it unnatural.

Do not add keywords mechanically.

Do not create thin pages merely to cover search phrases.

## 15. GEO and AEO

Content should be understandable to search engines and answer engines without sacrificing natural Latvian.

Prefer explicit entities, roles, actions, documents, conditions and outputs.

Important factual answers should be easy to extract from the page.

FAQ content must answer real questions and must not repeat the same information mechanically.

Do not generate artificial FAQ volume for schema or keyword coverage.

## 16. Images and visual material

Prefer real work and useful evidence:

- construction photos;
- project documentation;
- drawings;
- technical diagrams;
- plans;
- tables;
- process schemes;
- screenshots where they genuinely help.

Avoid filler stock imagery and AI-looking construction imagery.

Generated visuals must not create false evidence of ASTRO projects, employees, clients or completed work.

For relevant images check:

- filename;
- alt text;
- crawlability;
- dimensions;
- compression;
- responsive delivery;
- LCP risk;
- CLS risk;
- Open Graph use.

Prefer normal daylight and realistic construction environments over artificial cinematic styling.

## 17. Accessibility

Accessibility is part of implementation quality.

Relevant changes must consider:

- semantic structure;
- heading order;
- labels;
- keyboard use;
- focus states;
- contrast;
- interactive target size;
- reduced-motion expectations where relevant;
- image alternatives;
- form errors;
- screen-reader clarity.

Do not sacrifice accessibility for visual effect.

## 18. Performance and Core Web Vitals

Performance is a product requirement.

Avoid unnecessary:

- JavaScript;
- dependencies;
- animation;
- layout shifts;
- blocking resources;
- oversized images;
- duplicate assets.

For changes affecting the first viewport, shared layout, images, fonts or scripts, evaluate LCP, CLS and INP risk.

Do not trade meaningful performance for decorative behavior with little user value.

## 19. Analytics and privacy

Analytics should answer useful business questions.

Where relevant, define:

- what interaction matters;
- what event should be measured;
- what conversion it represents;
- what page or funnel it belongs to.

Avoid collecting data without a clear purpose.

Respect privacy requirements and existing consent architecture.

Do not introduce tracking libraries casually.

## 20. Development principles

Inspect dependencies before implementation.

Confirm the current architecture and root cause before changing code.

Prefer the smallest maintainable implementation that solves the problem.

Do not perform unrelated refactoring, cleanup or formatting.

Do not change user-facing approved copy unless the task explicitly authorizes it.

Preserve the existing architecture and design system unless evidence justifies change.

Shared components require regression awareness across all dependent routes.

## 21. Codex task discipline

Codex tasks must be narrow and explicit.

Codex prompts must be written in English.

Require Codex to:

- work and report in English;
- preserve user-facing Latvian text exactly when marked approved;
- obey AGENTS.md and AGENTS.override.md;
- inspect before modifying;
- avoid unrelated changes;
- identify affected dependencies;
- verify the implementation.

Use the workflow:

strategy -> scoped prompt -> inspect -> implementation -> checks -> review -> verification.

Detailed model selection, reasoning level, subagent use and context-control rules belong in `CODEX_ORCHESTRATION.md`.

## 22. Verification

For meaningful UI work verify both desktop and mobile.

Where relevant check:

- rendering;
- overflow;
- navigation;
- interactions;
- console;
- forms;
- links;
- responsive behavior;
- accessibility;
- metadata;
- schema;
- canonical;
- page-specific dependencies;
- shared-component regressions;
- Core Web Vitals risk.

Verification must match the actual scope of the change.

Do not claim a check was performed unless it was performed.

## 23. Git and release discipline

Never delete, reset, overwrite, commit or deploy unrelated user changes.

If the working tree is dirty or diverged, use a clean worktree from production.

Commit, push and deploy only when explicitly requested and within the approved scope.

Use this release sequence:

state -> scoped diff -> checks -> scoped commit -> push -> deployment -> live verification.

Google Search Console indexing requests are performed only when they are in scope.

Final implementation reports should state:

- changes;
- files;
- checks;
- commit;
- deployment;
- remaining risks or blockers.

## 24. Approved content

Approved user-facing copy is immutable unless the user explicitly asks to change it.

Do not:

- rewrite;
- shorten;
- improve;
- paraphrase;
- translate;
- complete;
- normalize

approved copy during implementation.

If technical implementation requires a content change, stop that part of the implementation and explain exactly why.

## 25. Existing decisions

Previously approved architecture, content, UX and design decisions must be preserved.

A historical conversation is not automatically an approved decision.

The latest explicit approval takes precedence over earlier drafts.

Important stable decisions should be recorded in `DECISIONS.md`.

## 26. Specialized rule files

Use the relevant specialized project files instead of loading every rule file for every task.

Active specialized files:

- `CODEX_ORCHESTRATION.md` - model routing, reasoning levels, subagents, context control, implementation workflow.
- `PRODUCT_UX_SEO.md` - detailed product, UX/UI, design-system, SEO, GEO/AEO, CRO, accessibility, analytics, privacy, security and CWV rules.
- `CONTENT_RULES.md` - detailed Latvian content, terminology and writing rules.
- `DECISIONS.md` - approved project decisions and current approved baselines.

For a simple task, use only the relevant rule set.

For a consequential cross-domain decision, consult this file and every specialized file that materially affects the decision.

Do not treat historical chats as a substitute for the current rule files when the rule files already cover the subject.

## 27. Quality standard

The target is not the minimum implementation that technically works.

The target is the most rational solution that balances:

- user value;
- business value;
- clarity;
- trust;
- conversion;
- search visibility;
- technical quality;
- accessibility;
- security;
- privacy;
- performance;
- maintainability;
- future development cost.

Do not increase complexity without corresponding value.

Do not reduce quality merely to save a small amount of implementation effort.

When a materially better long-term solution exists, surface it before implementing the weaker option.
