# ASTRO CONSTRUCTION - PRODUCT UX SEO

## 1. Purpose

This file defines the product, UX/UI, SEO, GEO/AEO, conversion, accessibility, performance and analytics standards for the ASTRO CONSTRUCTION website.

The site must be treated as a long-term digital product, not as a set of isolated pages.

The quality target is equivalent to a professional 50,000-100,000 EUR digital agency engagement.

The primary business goals are:

- qualified organic visibility;
- trust;
- qualified leads;
- conversion;
- strong information architecture;
- maintainability;
- technical reliability;
- long-term scalability.

Project Instructions and approved decisions remain higher priority.

## 2. Product principle

Every major decision should answer:

- who is this for;
- what problem does it solve;
- what should the user understand;
- what should the user do next;
- what evidence builds trust;
- what search intent does it serve;
- what business value does it create;
- what technical cost and regression risk does it introduce.

Do not add sections, pages, interactions or visual elements without a clear purpose.

## 3. Site architecture

The information architecture must help users find the right service or explanation without already knowing construction terminology.

Structure by user intent first.

Avoid requiring users to understand internal industry categories before they can navigate.

Good architecture should support:

- direct service discovery;
- problem-based discovery;
- expert information discovery;
- BIS/documentation discovery;
- logical internal linking;
- crawlability;
- future scale.

Do not create multiple pages with substantially the same commercial or informational intent.

Before adding a new page, check overlap with:

- existing service pages;
- expert pages;
- terminology pages;
- FAQ content;
- problem pages;
- planned pages.

## 4. Navigation

Navigation must be understandable to a normal client.

Users should be able to answer:

- where do I go if I know the service;
- where do I go if I only know the problem;
- where do I go if I need to understand a document or process;
- how do I contact ASTRO.

Avoid menu structures that mirror internal company organization.

Desktop and mobile navigation must be designed separately where interaction needs differ.

Check:

- label clarity;
- item count;
- grouping;
- hierarchy;
- discoverability;
- tap target size;
- keyboard use;
- open/close behavior;
- focus behavior;
- scroll locking;
- overflow.

## 5. Page types

Each page must have a defined role.

Typical ASTRO page roles:

- commercial service page;
- problem/solution page;
- expert informational page;
- construction term/document page;
- tool/calculator page;
- case/evidence page;
- category/hub page.

Do not mix several unrelated page roles unless there is a clear user benefit.

Commercial pages should convert.

Expert pages should answer and route to the relevant service where appropriate.

Tools should solve a real task and connect naturally to relevant services.

## 6. First viewport

The first viewport should make the page purpose clear quickly.

For commercial pages, the first screen should normally communicate:

- what ASTRO does;
- for whom;
- practical result;
- primary next action.

Avoid overloaded hero sections.

Do not place large decorative imagery above more useful content unless the image materially improves trust or understanding.

For expert pages, prioritize the answer and topic clarity over sales copy.

## 7. Information hierarchy

The page should be understandable even when scanned.

Use hierarchy through:

- heading levels;
- spacing;
- typography;
- grouping;
- visual contrast;
- progressive disclosure;
- content order.

Do not rely on decorative cards to create hierarchy.

The most important information should not be visually weaker than secondary information.

## 8. Cards

Cards are a tool, not the default layout.

Use cards when they improve:

- comparison;
- grouping;
- scanning;
- repeated interaction;
- structured choices.

Avoid long pages made entirely from similar cards.

If content is sequential, explanatory or hierarchical, prefer a clearer continuous structure.

## 9. Typography

Typography should support long-form technical reading.

Prioritize:

- readable body size;
- comfortable line length;
- clear heading hierarchy;
- sufficient line height;
- consistent spacing;
- visible links;
- strong mobile readability.

Do not use oversized display text if it reduces useful first-screen content.

Avoid excessive font weights and decorative typographic effects.

## 10. Spacing

Spacing should communicate structure.

Use consistent vertical rhythm.

Avoid:

- excessive whitespace that stretches simple content;
- compressed blocks that reduce readability;
- inconsistent section padding;
- random margins added to repair local layout issues.

Shared spacing should come from the design system where possible.

## 11. Visual style

The visual language should feel:

- modern;
- calm;
- technically credible;
- deliberate;
- clear.

Avoid:

- generic agency aesthetics;
- excessive gradients;
- decorative glass effects without purpose;
- noisy backgrounds;
- over-animation;
- artificial premium styling;
- visual trends that age quickly.

Construction credibility should come from content, evidence and clarity.

## 12. Design system

Prefer reusable design-system primitives.

Shared patterns should exist for:

- buttons;
- links;
- forms;
- inputs;
- alerts;
- tables;
- callouts;
- navigation;
- accordions;
- cards where appropriate;
- section headers;
- content widths;
- spacing;
- typography.

Do not create page-specific variants when a reusable pattern can solve the problem cleanly.

Do not force reuse when the existing component is structurally wrong for the new use case.

## 13. Responsive design

Responsive behavior must be designed, not merely compressed.

Check:

- hierarchy;
- reading order;
- touch targets;
- text wrapping;
- tables;
- cards;
- sticky elements;
- carousels;
- forms;
- navigation;
- long URLs;
- images;
- embedded visuals.

Do not assume desktop order is optimal on mobile.

Test representative intermediate widths when a component changes structure.

## 14. Mobile

Mobile is a primary experience.

Prioritize:

- fast orientation;
- readable text;
- clear primary action;
- short interaction paths;
- stable layout;
- no horizontal overflow;
- comfortable tap targets.

Avoid:

- tiny text;
- horizontally squeezed desktop components;
- hover-dependent behavior;
- excessive sticky UI;
- carousels that trap scrolling;
- large decorative content before the answer.

## 15. Sticky UI

Use sticky elements only when they provide continuous value.

Good examples:

- useful article navigation;
- clearly needed action;
- contextual progress/navigation.

Check:

- viewport height;
- mobile behavior;
- overlap;
- keyboard focus;
- sticky footer/header conflicts;
- content obstruction.

Do not use multiple competing sticky elements.

## 16. Interaction design

Interactions should be obvious and predictable.

Prefer native browser behavior when it is sufficient.

For custom interactions check:

- discoverability;
- hover;
- focus;
- keyboard;
- touch;
- loading state;
- error state;
- reduced motion;
- screen-reader name/state.

Avoid interaction for decoration alone.

## 17. Animation

Animation should improve:

- orientation;
- state change;
- feedback;
- perceived continuity.

Avoid:

- autoplay that distracts;
- unnecessary scroll animation;
- heavy reveal effects;
- movement that delays reading;
- motion that harms performance.

Respect reduced-motion preferences where relevant.

## 18. Forms

Forms should ask only for information that is useful at that stage.

For each field define why it is needed.

Use:

- clear labels;
- visible required state;
- useful error messages;
- correct input types;
- autofill where appropriate;
- predictable submit behavior.

Avoid placeholder-only labels.

Do not ask for project details that can reasonably be collected after initial contact unless they improve lead qualification materially.

## 19. Conversion

Conversion design should help the user take the next logical action.

Primary conversion goals may include:

- consultation request;
- document review request;
- cost estimate request;
- contact;
- tool use that leads to a relevant service.

Do not add CTAs mechanically after every section.

Use CTA where user intent and readiness support it.

Commercial CTAs should be specific to the service.

## 20. Trust

Trust should come from verifiable evidence.

Strong trust elements include:

- exact service scope;
- clear process;
- real documents;
- real project material;
- professional qualifications where verified;
- legal/company details;
- transparent price logic;
- clear limitations;
- useful technical content.

Avoid generic trust badges or unsupported claims.

## 21. Social proof

Use reviews, project references or numbers only when verified.

Do not invent:

- client logos;
- project counts;
- success rates;
- testimonials;
- statistics.

If a testimonial is used, preserve its real meaning.

## 22. SEO decision standard

SEO decisions must support real search intent and useful content.

Before new pages or major rewrites, evaluate:

- GSC data;
- keyword/query demand;
- search intent;
- SERP composition;
- competitors;
- current ranking pages;
- internal overlap;
- cannibalization risk;
- commercial value;
- content quality potential.

Do not create a page because a keyword can be targeted.

## 23. Search intent

Identify the primary intent:

- informational;
- commercial;
- navigational;
- transactional;
- mixed.

Do not force a service page to rank for a primarily informational query if an expert page would serve it better.

Do not make an informational page artificially commercial.

## 24. Page targeting

Each important page should have a clear primary topic and intent.

Avoid targeting several unrelated high-value queries on one page.

Avoid splitting one clear intent across multiple weak pages.

Use supporting sections and internal links instead of unnecessary page proliferation.

## 25. On-page SEO

For relevant pages review:

- title;
- meta description;
- H1;
- heading hierarchy;
- main content;
- canonical;
- internal links;
- image alt;
- schema;
- indexability;
- crawlability;
- duplicate content;
- URL;
- breadcrumbs where appropriate.

Metadata should describe the actual page.

Do not write clickbait titles.

## 26. Titles

Page title should:

- reflect real search intent;
- make sense to a human;
- differentiate the page;
- avoid keyword stuffing.

Use business/brand terms where useful, not mechanically.

## 27. Meta descriptions

Meta description should help CTR by clarifying:

- what the page contains;
- practical value;
- relevant differentiator.

Do not promise content or pricing the page does not provide.

## 28. H1 and headings

Use one clear H1.

Heading structure should represent content hierarchy.

Do not use heading levels for visual styling only.

Avoid repeating the page title mechanically in several headings.

## 29. Internal linking

Internal linking should help both users and search engines understand relationships.

Link when the next page genuinely helps.

Use descriptive anchor text.

Priority internal-link relationships include:

- expert page -> relevant service;
- service page -> relevant expert explanation;
- term/document -> related BIS/process page;
- tool -> related service;
- related documents/processes -> each other.

Avoid excessive cross-linking for SEO alone.

## 30. Hub pages

Use hub/category pages when they improve discovery and site architecture.

A hub should provide:

- useful orientation;
- clear grouping;
- distinct destinations;
- real content value.

Do not create thin category pages that exist only to hold links.

## 31. Cannibalization

Before creating or substantially changing a page, check whether another page already serves the same query intent.

If overlap exists, decide between:

- strengthening one page;
- merging;
- differentiating intent;
- redirecting;
- changing internal linking.

Do not solve cannibalization only by changing a few keywords if page intent remains duplicated.

## 32. Indexing

Index only pages with standalone value.

Consider noindex for pages that are:

- utility-only with no search value;
- duplicate;
- temporary;
- internal;
- thin and not intended for search.

Do not noindex valuable pages casually.

Check canonical and internal linking together with indexation decisions.

## 33. Canonical

Canonical should reflect the intended indexable URL.

Avoid:

- self-conflicting canonicals;
- canonicals to unrelated pages;
- canonical changes as a substitute for proper redirects.

Verify route behavior and redirect behavior where URLs changed.

## 34. Structured data

Use schema only when it matches visible page content.

Possible relevant types include:

- Organization;
- LocalBusiness where appropriate;
- Service;
- FAQPage where eligible and useful;
- BreadcrumbList;
- Article where appropriate.

Do not add schema solely to maximize markup volume.

Keep visible content and structured data consistent.

## 35. FAQ schema

FAQ schema should reflect real visible FAQ.

Do not create hidden or schema-only questions.

Do not duplicate several near-identical questions.

Schema parity must be checked after content edits.

## 36. GEO/AEO

Optimize content for answer engines through clarity, not artificial AI wording.

Prefer:

- explicit facts;
- named entities;
- exact roles;
- exact document names;
- direct answers;
- clear conditions;
- structured content;
- consistent terminology.

Important answers should be understandable outside the full page context.

Do not write artificial "AI summary" sections unless they help users.

## 37. Entity clarity

Use consistent naming for:

- ASTRO CONSTRUCTION;
- services;
- documents;
- professional roles;
- Latvian authorities;
- BIS;
- locations.

Avoid switching terminology unnecessarily.

Entity consistency supports both comprehension and machine interpretation.

## 38. Local SEO

Primary market is Latvia.

Local relevance should come from:

- real service area;
- correct business data;
- Google Business Profile;
- relevant Latvian terminology;
- location-specific content where there is real value.

Do not create city pages at scale without demonstrated search/commercial value.

Avoid doorway-style location pages.

## 39. Google Business Profile

GBP content and website content should be consistent.

Where relevant ensure:

- business name;
- categories;
- service areas;
- services;
- contact details;
- landing pages

match the real offering.

Do not create unsupported category or location claims.

## 40. Image strategy

Images must serve at least one purpose:

- evidence;
- explanation;
- orientation;
- trust;
- process understanding;
- visual differentiation.

Prefer:

- real work;
- real construction environments;
- documents;
- drawings;
- plans;
- diagrams;
- tables;
- execution details.

Avoid filler imagery.

## 41. AI-generated images

AI-generated imagery may be used only when it does not imply false evidence.

Do not generate visuals that appear to document:

- ASTRO projects;
- ASTRO employees;
- real clients;
- actual completed work

when they are not real.

Generated explanatory diagrams or conceptual visuals should remain clearly illustrative.

Avoid an obvious AI look.

## 42. Image SEO

For important images check:

- descriptive filename;
- relevant alt;
- width/height attributes;
- responsive sizing;
- compression;
- crawlability;
- lazy loading;
- LCP priority;
- caption where useful;
- Open Graph use where relevant.

Do not stuff keywords into alt text.

## 43. LCP images

For likely LCP images:

- avoid unnecessary lazy loading;
- use correct dimensions;
- use suitable format;
- avoid oversized source files;
- preload only when justified;
- verify actual LCP candidate.

Do not prioritize decorative images over content.

## 44. CLS

Prevent layout shift through:

- explicit media dimensions;
- stable font behavior;
- reserved dynamic space;
- predictable banners;
- controlled sticky elements.

Do not inject large elements above existing content after load.

## 45. INP

Protect interaction responsiveness.

Avoid:

- unnecessary JavaScript;
- large main-thread tasks;
- heavy event handlers;
- repeated layout calculations;
- interaction effects with little value.

Prefer native CSS/HTML behavior where possible.

## 46. Core Web Vitals

CWV is a product quality requirement.

For major frontend changes evaluate:

- LCP;
- CLS;
- INP.

Use field data where available.

Do not rely only on Lighthouse when real field data exists.

## 47. Accessibility

Target robust accessible behavior.

Check:

- semantic HTML;
- heading order;
- keyboard navigation;
- visible focus;
- form labels;
- error communication;
- contrast;
- link clarity;
- interactive target size;
- ARIA only where needed;
- reduced motion;
- image alternatives.

Accessibility defects are product defects.

## 48. Semantic HTML

Prefer native elements:

- button for actions;
- a for navigation;
- label for form controls;
- table for tabular data;
- nav for navigation;
- main for primary content.

Do not recreate native controls with generic divs unless unavoidable.

## 49. Keyboard

All interactive UI must work without a mouse.

Check:

- tab order;
- focus visibility;
- escape behavior where relevant;
- menu controls;
- accordions;
- modal behavior;
- carousel controls.

Avoid focus traps unless the component intentionally requires one and handles it correctly.

## 50. Contrast

Maintain readable contrast.

Do not lower contrast for aesthetic subtlety when it harms readability.

Check:

- body text;
- small labels;
- placeholders;
- disabled states;
- links;
- focus rings.

## 51. Tables

Technical tables should remain usable on mobile.

Options include:

- responsive horizontal scroll;
- stacked presentation;
- simplified mobile view.

Choose based on actual comparison needs.

Do not break semantic table structure unnecessarily.

## 52. Accordions

Use accordions when hiding secondary detail improves scanning.

Do not hide critical information that the user must see to make a decision.

Accordion controls must expose:

- state;
- keyboard behavior;
- clear labels.

FAQ does not automatically require accordion UI.

## 53. Carousels

Use carousels only when multiple related visuals genuinely benefit from the format.

Avoid carousels for primary content that should simply be visible.

Check:

- swipe;
- controls;
- autoplay;
- pause behavior;
- keyboard;
- mobile overflow;
- accessibility;
- CLS.

Autoplay should have a strong reason.

## 54. Analytics

Analytics should support decisions.

Relevant questions include:

- which landing pages produce qualified contacts;
- which services attract organic traffic;
- which expert pages lead to service pages;
- where users abandon forms;
- which tools are used;
- which CTA types convert;
- which traffic sources produce leads.

Do not track events without a decision use case.

## 55. GA4 events

Event naming should be consistent.

Track meaningful actions such as:

- form start;
- form submit;
- phone click;
- email click;
- document upload start;
- key CTA click;
- calculator completion

only when they support analysis.

Avoid excessive micro-event noise.

## 56. Conversion definitions

Define conversions explicitly.

A page view is not automatically a conversion.

Differentiate:

- lead;
- qualified lead;
- contact action;
- micro-conversion;
- tool engagement.

Use this distinction when interpreting analytics.

## 57. Search Console

Use GSC for:

- query discovery;
- CTR opportunities;
- ranking movement;
- page overlap;
- indexing;
- new-page validation;
- query/page matching.

Do not use impressions alone as proof of commercial value.

## 58. SEO content decisions from GSC

Before creating a new page from GSC data, check:

- whether an existing page already ranks;
- query intent;
- landing page;
- average position;
- CTR;
- query variants;
- commercial relevance.

A new page is justified only when it can serve a distinct intent better.

## 59. Competitor analysis

Competitor analysis should identify:

- SERP composition;
- page type;
- content depth;
- UX patterns;
- trust elements;
- pricing transparency;
- internal linking;
- visual evidence;
- schema;
- weaknesses ASTRO can solve better.

Do not copy competitor structure mechanically.

A competitor ranking does not prove their UX or content is good.

## 60. Research quality

For consequential decisions use current evidence.

Distinguish:

- observed data;
- verified fact;
- hypothesis;
- recommendation.

Do not present assumptions as evidence.

## 61. New page gate

Before building a new page, answer:

1. What exact user intent does it serve?
2. Is that intent already served?
3. Is there measurable or credible demand?
4. What SERP type ranks?
5. What business value does it create?
6. Can ASTRO provide genuinely better content?
7. How will users reach it?
8. How will search engines discover it?
9. What page links to it?
10. What does it link to?
11. What conversion path follows?
12. What evidence or visuals improve it?

If these questions do not have a strong answer, do not build the page yet.

## 62. Major redesign gate

Before major UI changes, evaluate:

- current problem;
- analytics evidence;
- mobile behavior;
- desktop behavior;
- navigation impact;
- content hierarchy;
- conversion impact;
- accessibility;
- CWV;
- implementation cost;
- regression scope.

Do not redesign because a page feels visually old without identifying the actual problem.

## 63. Shared component gate

Before changing a shared component:

- list dependent routes;
- identify variants;
- inspect mobile behavior;
- inspect accessibility behavior;
- inspect SEO/semantic impact;
- define regression checks.

Do not optimize one page by breaking a shared pattern elsewhere.

## 64. Technical simplicity

Prefer simple architecture when it provides the same product result.

Avoid adding:

- dependencies;
- frameworks;
- scripts;
- abstractions

without clear value.

Do not let design complexity exceed user value.

## 65. Maintainability

A good implementation should be understandable by the next developer.

Prefer:

- predictable structure;
- reusable tokens;
- consistent naming;
- limited variants;
- clear dependencies;
- local responsibility.

Avoid one-off overrides that accumulate technical debt.

## 66. Privacy

Collect only data needed for the business purpose.

Respect:

- consent architecture;
- cookie requirements;
- form privacy;
- third-party embeds;
- analytics settings.

Do not add trackers or embeds casually.

## 67. Security

For forms and dynamic features consider:

- validation;
- spam protection;
- rate limiting where relevant;
- safe file handling;
- dependency security;
- exposure of internal data.

Do not trade security for convenience.

For any form, upload, dynamic endpoint or third-party integration, include security review in the implementation scope when the change materially affects data handling.

## 68. Content-design coordination

Design must support the actual approved content.

For visible wording, `CONTENT_RULES.md` is the detailed language authority.

Do not force content into a component that requires rewriting it.

If approved content is too long for a proposed layout, change the layout.

Do not truncate important technical information solely for visual symmetry.

## 69. SEO-design coordination

SEO requirements should influence structure early.

Before final UI, ensure the design supports:

- crawlable text;
- semantic headings;
- visible useful content;
- descriptive links;
- schema parity;
- indexable routes.

Do not hide essential content behind interactions that reduce crawlability or usability.

## 70. Accessibility-design coordination

Accessibility is part of design definition.

Component approval should include:

- focus state;
- keyboard state;
- error state;
- mobile state;
- reduced-motion behavior where relevant.

Do not leave accessibility to post-launch repair.

## 71. Performance-design coordination

Before approving heavy visual features, consider:

- asset size;
- JS requirement;
- LCP;
- CLS;
- INP;
- mobile hardware.

If a decorative effect has meaningful cost and little user value, remove it.

## 72. Review checklist for a major page

Before approving a major page, check:

### Product
- clear purpose;
- clear audience;
- clear next action;
- useful content order.

### UX
- understandable navigation;
- strong hierarchy;
- desktop/mobile;
- no overflow;
- predictable interactions.

### UI
- design-system consistency;
- readable typography;
- useful visuals;
- no decorative clutter.

### SEO
- intent;
- title;
- H1;
- metadata;
- canonical;
- internal links;
- schema;
- indexability.

### GEO/AEO
- direct answers;
- explicit entities;
- exact terminology;
- extractable facts.

### CRO
- relevant CTA;
- trust;
- friction;
- form quality.

### Accessibility
- semantics;
- keyboard;
- focus;
- contrast;
- labels.

### Performance
- LCP;
- CLS;
- INP;
- image weight;
- JS weight.

### Analytics
- meaningful events;
- conversion definition.

### Maintenance
- reusable patterns;
- no unnecessary one-offs;
- clear dependencies.

## 73. Final product standard

A strong ASTRO page should:

- answer a real user need;
- be understandable without construction education;
- provide technical credibility;
- feel visually calm and intentional;
- work well on mobile;
- load quickly;
- be accessible;
- target a real search intent;
- support Google and answer engines;
- provide a clear next step;
- use evidence instead of generic marketing;
- fit the long-term site architecture.

The site should become easier to understand and maintain as it grows, not more fragmented.
